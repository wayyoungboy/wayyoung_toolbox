# 完整媒体中心目标与验收范围

## 用户确认的目标

面向个人使用，完整保留 Peach 的用户可见功能，以 Go 实现服务端，并融入现有飞牛工具箱，替代用户日常使用的飞牛影视。

这是一项完整媒体产品建设任务。元数据检查与修复只是其中一个能力，不能以刮削页面、NFO 修复工具或播放演示作为最终交付。

建议使用下面的文字设定项目目标：

> 将现有飞牛工具箱的影片采集模块升级为完整个人媒体中心。以已审定的 Peach 源码版本为功能基线，使用 Go 实现后端，提供统一的飞牛原生入口和适配桌面、手机浏览器的完整界面。保留馆藏管理、播放与字幕、个人记录、多来源元数据及演员资料、关注与发现、偏好分析、资源搜索、云下载、浏览器添加、整理维护和后台任务等全部用户可见能力，并保留现有 RSS、qBittorrent、JAVSP、翻译与去重流程。逐项完成自动化回归、打包、升级保留验证及 NAS 真实场景验收，使用户能在本应用中完成发现、下载、整理、浏览、播放和管理的完整流程。

## 功能基线与完成口径

- 上游项目：[peach-mitao/peach](https://github.com/peach-mitao/peach)。
- 本轮核对版本：[de22796c04919aaa057d77930c33c81313765569](https://github.com/peach-mitao/peach/commit/de22796c04919aaa057d77930c33c81313765569)。后续上游变化需单独更新基线和差异清单。
- 参考证据是该版本的 README、架构文档、路由注册、媒体响应、来源策略和专项文档；源码中存在接口不代表已在目标 NAS 或外部站点上实测成功。
- 本文是目标与设计，所有新能力均未因写入本文而变成已实现。实施时建立逐项交付表，记录对应界面、API、测试和实机证据。
- 面向单人使用。登录、媒体文件访问和外部播放链接仍须有适当的访问控制；不将单人使用等同于任何人可读写。
- 各阶段只是交付顺序，不缩减最终范围。尚未完成的基线功能必须继续列为待办，不能用“后续再做”标记项目整体完成。

## 架构与技术约束

### 应用归属与界面

- 开发主线为现有工具箱仓库的 `modules/media/`，继续复用工具箱的飞牛入口、模块生命周期、配置隔离和日志管理。
- 媒体模块升级为完整媒体中心，拥有面向观看的首页、馆藏、人物、发现、关注、播放与管理界面。下载采集和维护作为其中的管理能力，不把所有功能堆进任务表单。
- 提供直接打开媒体中心的入口，进入后能完成全部个人媒体工作流；保留工具箱总览的入口和状态。
- 前端仍使用适当的 Web 技术。Go 的要求针对业务服务端，不要求用 Go 绘制浏览器界面。需要复用或适配上游 React 代码时先记录许可证和修改范围。
- 所有界面共享同一媒体身份、任务状态和配置，避免出现两个不同的成功状态或重复配置页。

### Go 服务与媒体工具

- 业务服务继续在工具箱 Go 进程内运行；不依赖 Python Web 服务，也不以隐藏 Python 子进程代替尚未实现的来源或业务逻辑。
- FFmpeg、FFprobe 等专业媒体工具按需作为受管外部程序调用；它们不是额外的常驻业务服务。转码并发、生命周期、取消和缓存必须可观察、可收敛。
- 硬件转码以实际探测与实际编码为准；编译支持、设备节点存在或驱动名称不算解码/编码验收。
- 桌面浏览器采集、用户脚本等运行在用户设备上的配套能力须明确边界；NAS 服务不假装拥有桌面浏览器。

### 数据模型

- 新增持久媒体馆藏，作为本应用展示和播放的依据，不依赖飞牛影视的内部数据库或扫描缓存。
- 区分作品、版本/分卷、物理文件、人物/厂牌/标签、元数据候选/字段来源、图片资源、个人记录和后台任务。
- 文件扫描与下载入库都能登记到同一个馆藏。媒体文件的实际存在状态不能由“历史下载任务成功”推断。
- 保留用户手动修改、原始文件名与来源证据。完整番号无法确认时显示待复核，不把相似结果写为确定身份。
- 本应用中的资料修正直接反映到本应用页面；同名 NFO 是交换与兼容输出，不再以飞牛影视是否刷新作为本应用资料已更新的唯一依据。
- 新表和旧任务数据采用可追踪迁移；升级前备份，升级后检查配置、任务、记录与媒体关联。

### 外部来源与许可证

- 上游存在的站点功能按能力对齐，但不得把源码中已有解析器描述为“目标 NAS 已验证可用”。对登录、地区、限流与站点变化分别给出实际状态。
- 需要用户正常完成的来源登录、浏览器验证和账号授权，提供明确流程；不得用关闭 TLS 校验等手段掩盖不可用。
- Peach 基线是 AGPL-3.0-or-later。直接复用、修改或跨语言翻译的代码必须保留归属并履行相应许可证义务，不能因使用 Go 就删除上游许可。
- 实施前逐项标记复用、移植、已有 Go 能力和独立实现；对浏览器脚本、第三方资料及依赖分别登记来源。
- 更新和诊断机制适配本项目的发布与数据策略；不把应用自动接入上游的统计或研究收集服务。相关选择和实现状态必须在界面可见。

## NAS 平台差异的处理

| 差异 | 处理原则 | 不可省略的验收 |
| --- | --- | --- |
| NAS 无桌面浏览器 | 保留书签/历史文件导入；需要桌面环境的功能提供可选配套方式，具体方案待设计 | 文件导入先真实可用，配套方式未完成时继续列为缺口 |
| 某些来源依赖浏览器会话 | 评估用户设备上的正常会话配对或已有授权数据导入，不以运行环境缺失为成功 | 在目标运行环境独立验证，不能沿用上游桌面结果 |
| 云盘与 NAS 路径不同 | 配置真实挂载路径和渠道坐标；馆藏身份与路径变化分开 | 离线、恢复、移动挂载及下载落地后的关联 |
| 浏览器对编码的支持不同 | 保留直放、转封装、必要转码和外部播放器选择 | 桌面与手机浏览器、实际媒体格式分别记录 |
| 飞牛官方移动端和 TV 客户端 | 新媒体中心的 Web 功能不自动等于兼容官方客户端协议；本次用户确认的是 Peach 完整能力 | 桌面/手机 Web 必须可用；额外原生客户端若需要需单独定义协议与交付 |

平台差异是待解决的适配项，不能成为静默删除 Peach 功能的理由。无法原样落地时先提出能满足同一用户需求的替代方案，并保留未取得的验收证据。

## 实施顺序

1. **建立逐项功能清单和数据基础**：将上游所有用户入口、路由和专项能力映射到本表；确定数据模型、迁移、API、界面导航和复用许可。
2. **馆藏与播放闭环**：接入已有成品，完成馆藏、作品/人物详情、搜索、播放、字幕和个人记录，形成无需打开飞牛影视的真实观看流程。
3. **资料与管理闭环**：多来源、NFO、演员头像、字段冲突复核、图片工具、整理维护和现有下载流水线进入同一馆藏。
4. **完整 Peach 功能对齐**：跨站关注、发现、想要、偏好、浏览器资料、云下载、用户脚本、外部播放器等逐项闭环。
5. **全量验收与替代验证**：升级保留、后台恢复、媒体格式/设备回归、资源清理、完整功能表复核和个人真实使用验收。

各步骤可交付可用版本，但只有所有已确认功能均有实现和相应验收结论时，才可称为“完整替代版本”。

## 最终验收

- 从已有目录导入资料、查找作品、打开详情、选择版本、播放和继续观看，均在本应用完成。
- 从 RSS、用户脚本或手动资源入口开始，完成下载、落地、整理、登记馆藏和播放；已有文件能被识别并避免重复投递。
- 修改标题、演员或封面后，本应用页面和搜索结果一致，刷新或重启不回退。
- 同号不同版本、分卷、缺少前缀、冲突 NFO 和来源失败不导致错误关联或丢失原文件。
- 本地、挂载网盘、云下载渠道、跨站来源、在线字幕分别保留验证范围。外部服务暂不可用时明确原因，不假报成功；具备真实配置但仍未完成的端到端能力继续列为未验收。
- 任务取消、服务重启、网络失败和重试后状态一致；媒体服务没有失控的残留转码进程或无限增长缓存。
- 配置、凭据、任务、馆藏和观看记录经过升级保留验证；所有可用回滚范围和不可撤回操作在对应流程中准确说明。
- 对桌面与手机浏览器完成播放和导航验收；NAS 的实际硬件转码能力有运行证据。
- 新版本测试包经小样本调试和数据保留验证后，再完成用户确认范围的实际馆藏验收。功能目标本身不授权立即改写全库媒体或移除飞牛影视。
- 发布版本提供相符的源码、许可证、来源说明、安装升级文档和可检查的功能完成表。
