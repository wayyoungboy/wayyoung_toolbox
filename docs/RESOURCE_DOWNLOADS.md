# 显式资源下载（0.7.9 测试阶段）

这是个人媒体中心完整获取链路的一项增量。已接入资源选择、明确确认、只读核对、下载记录和队列跳转，0.7.9 FPK、NAS 安装保留与隔离浏览器端到端通过；没有投递真实资源。不能以此标记完整 F16 完成，完整渠道缺口仍见[后续契约](MEDIA_DISCOVERY_ACQUISITION.md)。

## 页面用法

1. “发现与采集 → 资源搜索”输入完整番号，点击搜索或读取上次结果；馆藏作品详情也能带入番号。搜索和打开页面不会自动下载。
2. 在本次成功结果中点击“选择下载”，核对 BTIH、搜索时间和下载目录，输入“下载资源”后才登记。目录来自“设置 → 下载入库”的来源目录；确认期间配置变化会拒绝新登记，要求重新读取。
3. “资源下载记录”每 5 秒只读刷新最近 20 项；点击原任务进入处理队列，查看下载、搬运、整理及馆藏登记的分别结果。已有任务按原 ID 返回，不因重复选择复活。

旧结果、失败缓存、查询中或已取消的查询不能提交下载。服务器明确拒绝时返回重新选择，不循环重发失效快照。若登记响应丢失、超过 30 秒或手动“停止等待”，先按番号和 BTIH 只读核对原任务；查不到不等于未登记，页面不会自动再发 POST。只有重新明确确认同一选择才可能再次登记，后台仍按原意图幂等。

界面显示“已登记”不等于“已下载”，远端报告下载完成也不等于“已整理/已入馆藏”。读数过期会显示错误及上次成功时间，不伪装为实时状态。取消只停止本地处理，不能用来停止远端 qB 下载。

## 独立生产者与共享执行

搜索继续只读，只有显式 POST 才登记下载意图。选择必须来自同一成功缓存快照中的完整番号、来源和 BTIH；客户端不能传磁力、站点 URL、下载器地址、凭据或目标路径。缓存已失败、被替换或不含该候选时拒绝新建，要求重新读取/搜索。

`MediaJob.Resource` 保存来源、搜索时间、规范磁力、当时的下载目录及不可逆的下载器身份摘要；没有创建 RSS 任务，也不写 `seen_items`。凭据仍只在应用私有设置中，地址与账号不原样进入账本。资源生产者与 RSS 共用已有的持久媒体队列、事件、预占和投递执行器，不新增常驻进程。

在同一 SQLite 事务中核对缓存和现有任务，再预占番号/种子。重复请求返回原任务，不重置已取消、失败或已完成的状态；已有 RSS 或影片处理记录也会复用，而非另投一次。相同种子不能用另一个番号重新绑定。缓存后来被轮转或设置变化，不使已登记意图消失。已登记过的请求需要通过原任务的明确重试处理，不靠重复 POST 重新下载。

下载目录在登记时固定。下载器地址和账号形成不含密码的身份摘要；密码轮换不会改变任务身份，切换实例或账号则暂停旧任务的查询和操作。当前只支持恢复原下载器后继续，没有自动猜测实例迁移的重新绑定功能。

## 状态与恢复

| 阶段/证据 | 实际含义 |
| --- | --- |
| `discovered / pending` | 已保存用户选择，尚未确认远端任务 |
| `submission_dispatching` 事件 | 在发出 qB POST 前持久记录，不等于已成功下载 |
| `acknowledged` | qB 接受请求，仍须查询确认任务身份 |
| `download / pending` | 已绑定规范 hash + AddedOn，下载观察独立轮询 |
| `download.complete` | 远端报告完成，不直接授权搬运或标记已入库 |
| `transfer / qb_cleanup` | 现有入库流程重新核对完成、实例、路径和文件身份，确认停止后搬运；保留原任务 ID |
| `done` 与整理子任务 | 搬运/远端记录清理完成；子任务保留资源来源，再走整理及可选馆藏登记，不能当作已经入库 |

明确拒绝投递才允许通过任务重试再发 POST。响应丢失、取消中断或重启留下的 `dispatching / acknowledged` 仅观察原种子，不盲目重发；只有落在原投递时间窗内的 AddedOn 才能确认。已绑定后还需精确匹配同一 AddedOn，不把同 hash 的后续重新添加任务接管为旧任务。

下载完成发现会沿用原资源任务；未确认或已取消的任务不会被入库发现旁路。搬运成功后即使后续整理/登记失败，也不重新投递资源。原 RSS 去重、配置和旧持久任务继续保留。

**现有队列“取消”只停止本地处理/跟踪，不承诺远端下载已停止，也不会永久删除远端文件。**远端取消的确认交互尚未接入；界面不得将该动作命名为“已取消远端下载”。云下载、完整下载统计/独立状态页和主动重新下载政策也仍需补齐。

## API

以下路径相对于媒体模块。GET 只读本地账本，最多返回 100 项；POST 要求管理员、同源、进程级 CSRF token、JSON 和明确确认词。

```text
GET  /api/resources/downloads?limit=20
GET  /api/resources/downloads/selection?code=TEST-001&provider=javdb&infohash=<BTIH>
POST /api/resources/downloads
     {"code":"TEST-001","provider":"javdb",
      "infohash":"0123456789abcdef0123456789abcdef01234567",
      "searched_at":"<当前成功搜索的 searched_at>",
      "intake_revision":0,
      "confirmation":"下载资源"}
```

`intake_revision` 必须使用刚读取的 `/api/intake` 配置版本，而不是固定填写示例中的 0。POST 只持久登记，由进程内队列执行；新建返回 202，已存在返回 200，均包含 `job / created`。200/202 不表示已下载。列表 GET 返回 `items`；selection GET 返回 `job` 或 `null`，可核对较早的资源/订阅 owner，不依赖最近 20 项或搜索缓存。二者都不请求 qB 或来源。原任务详情、事件和重试沿用处理队列 API。

## 当前证据与尚缺验收

- 每阶段先执行 RED 再提交最小实现及 GREEN。覆盖独立来源、精确缓存快照、无效输入、目录固定、密码不入账本、重启、与 RSS 双向预占、明确拒绝、结果不确定、投递中取消、AddedOn 重加、实例变化前零网络访问、原 ID 搬运与整理子任务来源。
- 16 个并发请求只创建一个生产者；注入事件写入失败时任务与事件一起回滚。缓存轮转后重复请求不复活已取消意图。
- 全仓库 Go race/vet 与资源/RSS/入库专项通过；新增生产者/API 两文件专项语句覆盖率 86.9%，不是整个媒体模块覆盖率。x86_64 FPK、打包目录和 ARM64 Go 交叉编译通过。
- 浏览器使用真实 HTTP/SQLite 与合成 qB，覆盖确认/返回、双击、挂起 CSRF 请求停止、明确 409 后重新选择、已提交但响应丢失后的 GET 核对、下载进度与过期读数、取消后重复选择、桌面/手机/深色。旧搜索和完整馆藏旅程另外回归，未用纯前端 mock 冒充投递链路。
- NAS 重跑新链路及原馆藏播放旅程通过，安装前后 31 张表与配置摘要一致。测试只用临时中性文件，不是真实资源下载验收。完整版本、环境及边界见[阶段说明](MEDIA_CENTER_STATUS.md)。
